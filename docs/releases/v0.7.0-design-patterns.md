# nuikit design patterns: what the owner picked on the experiment server (draft for systemizing)

These patterns came out of the owner's in-game feedback on 2026-10-21. This is the raw material; the lead's agent turns it into
`docs/design.md` rules, registry components and lint checks. Quotes are the owner's words.

## 1. Surfaces: one family, two placements

Every window is a **shadcn Sheet** (or Drawer, where the Radix modal problem doesn't apply). Hand-built boxes are out.
> "the context as built on that shadcn model is performing perfectly … that should generally be the basis for a lot of floating context windows and systems"

| Placement | When to use it | Live examples |
|---|---|---|
| **Flush** (`edge-sheet variant="flush"`): touches the screen edges, a backdrop surface, the content in an inner column | **The game is paused or replaced.** System-level, takes over the screen, one per screen: the pause menu, the full map, character select/creation | the pause menu |
| **Floating** (`variant="floating"`, the default): inset `--nk-edge` (1.5rem) on every side, border all round, the identity's corner shape on every corner, the panel shadow | **The game keeps running behind it.** Contextual, opened from the world, often paired or stacked: inventory, shops, banking, clothing, job menus, context menus, dialogs, trays | inventory sheets, the bottom action tray |
| **Tray**: a floating bar along the bottom, never touching the screen bottom | actions and key hints for the window above it | inventory use/give/amount |

> "it may not always be appropriate for everything to touch screen edge … same for the interaction block along the bottom. it doesnt feel right for the bottom bar to touch bottom of the screen."

**Proposed rule (for discussion):** flush is reserved for one top-level system screen at a time; everything else floats. Job and resource menus are always floating. They pick a side (right for menus opened from the world, left for "your stuff") and never design their own frame.

## 2. Structure inside a surface: rows, not cards
- Rows of 48px with hairline dividers, sections split by Separators, and one ScrollArea column with a gutter so the scrollbar never covers content.
- **Sub-pages swap in place** inside the same sheet, with a back row and Esc for back; they never open extra cards beside it.
- Exactly one primary action per surface, drawn as a filled bar; key hints as key caps.

> "going for simple design systems that are compact intuitive and arent over abundant in square card geometry is smoother"

## 3. Motion system
- Surfaces slide in from their edge, with rows staggering in after; they slide out on close (nuikit-core `<Surface>` with `useSurfaceOpen()`). Input is released immediately on close.
- **Text roll** (`TextRoll` / `NumberRoll`) for any value that changes in place: location, money, counts, labels.
  - The roll is **vertical only**; alignment is resolved per layer.
  - Width changes move neighbours, never the rolling text. A centred label must not travel diagonally.
  - "the text rotation mechanics are phenomenal … we need to make that more automatic and clean as a utility such that it just naturally works"
- **Smooth caret and typing** (`SmoothInput`) on every text field.
- Every animation obeys `/nuikit motion off` (instant) and reduced motion (a fade of 100ms or less).
- "introducing features of smooth animation behavior and design across the board … an out of the box feature"

## 4. Values traced on shape
- Levels (vitals, durability, weight) are drawn **along the element's own outline**, following the identity's shape (radius, pill, chamfer), never as a circle inside a square.
- One chip family for every vital; no labelled special cases ("why wouldnt they just be like the others. we want to streamline").

## 5. Camera
- Focus cameras **never force rotation**: they keep the player's current view and move in on the character in the clear area beside the surfaces ("not force rotation, that could cause some motion sickness").
- Surfaces report their clear area (`pause:preview:frame`, `inventory:frame`) and the camera frames into it.

## 6. Replace native, fully
- nuikit's own screens should be complete replacements, e.g. the pause map shows every native blip, filters them, and click sets a waypoint ("we want our own menu system to be completely replacement to the native systems").

## 7. Open questions for the lead
- Do job menus get a shared "job sheet" template (header, duty toggle, rows, tray), so resources stop designing their own?
- Does `variant` default by context (opened from the world → floating; system → flush) via the surface API rather than by each author?
- Drawer (vaul) is always modal in Radix and breaks drag between panels. Does it stay for trays without drag, or is it dropped in favour of Sheet?

## 8. Lighting
- The focus camera's studio light is **off by default** ("kill the studio light effect on the pause and inventory"). Keep it as an option and grow it into a lighting-preset utility surfaces can opt into ("lighting tools are a powerful system").

## 9. Vital anatomy (prototype in progress)
- A vital is composed of parts: Shape (square, rounded, circle, diamond, hex, chamfer), Level (outline, liquid fill, bar), Icon (vital colour or uniform), Label attach (inline, tag/crest, flag), Pop (transient name + delta on change).
- Every shape is one SVG path; border, clip, trace, fill mask and label anchors all derive from it, so a new shape is one function.
- The theme picks the variant per part with tokens (`--nk-chip-shape`, `--nk-level-style`, `--nk-label-attach`, `--nk-vital-icon`).
- Hierarchy: voice and radio are the primary, always-on layer; vitals are secondary and surface only on change or threshold.

## 10. Universal glue: conventions over custom
- nuikit connects to the infrastructure servers already have (image packs, item images, vehicle images, popular resources) through configurable templates with silent fallbacks, never a nuikit-only format ("we want to be a universal glue, not one only for certain surfaces").
- Every image goes through one resolver (kind + key, then candidate URLs, then an icon fallback), configured per server.
